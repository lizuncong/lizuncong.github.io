# 数据库时间类型科普：DATETIME、TIMESTAMP、BIGINT

## 问题的起点

在数据库里存“一个时间”听起来很简单，但不同类型的底层机制完全不同，选错了会埋下时区 bug。下面用具体例子把三种类型从写入到读取讲清楚。

---

## 1. DATETIME——裸字符串

**底层机制**：存一个格式化字符串，不带任何时区信息。

### 写入时发生了什么

`CURRENT_TIMESTAMP` 是一个数据库函数，它的返回值**取决于数据库服务器当前配置的时区**：

```
数据库时区配置为 +08:00 → CURRENT_TIMESTAMP 返回 "2026-09-21 10:21:00"
数据库时区配置为 +00:00 → CURRENT_TIMESTAMP 返回 "2026-09-21 02:21:00"
```

DATETIME 列不做任何换算，给它什么字符串就存什么字符串。

### 读取时发生了什么

完整链路：**数据库 → 驱动 → 应用程序 → 展示层**。每一层都有可能引入误解。

**第一步：数据库返回原始字符串**

```
SELECT created_at;
→ 驱动收到字节流："2026-09-21 02:21:00"
```

数据库原样返回，不做任何解释。

**第二步：驱动把字符串变成程序中的时间对象**

驱动必须把这串字符变成编程语言里的时间类型（比如 Go 的 `time.Time`、Java 的 `LocalDateTime`）。但驱动**不知道**这串数字是哪个时区的。

驱动的 `loc` 配置就是在回答这个问题——它相当于一个约定：

> “我认定数据库里存的墙钟都是 X 时区的。”

驱动把这串数字原样装进时间对象的时钟字段（年月日时分秒不变），贴上 X 时区标签：

```
驱动配置 loc = +08:00（上海）
驱动产出：2026-09-21 02:21:00 +08:00
         ↑ 数字没变，只是说"这是上海的 02:21"
```

如果数据库确实存的是上海墙钟，还原正确。如果实际存的是 UTC 墙钟，数字没错但标签贴错了——后续所有环节都基于这个错误理解。

**第三步：应用程序拿到时间对象**

此时应用代码拿到的是一个带有错误时区标签的 `time.Time`。它不做任何检查（也没有能力检查），直接往下传。

**第四步：序列化给前端**

`time.Time` 序列化成 JSON 时输出 RFC 3339 格式：

```json
"created_at": "2026-09-21T02:21:00+08:00"
```

**第五步：前端格式化展示**

前端拿到这个带时区的时刻，用 `Intl.DateTimeFormat` 按浏览器所在时区格式化：

```
用户在上海 → "02:21"
用户在纽约 → "2026-09-20 13:21"（同一时刻在纽约的墙钟）
```

前端没做错任何事，它忠实地展示了后端给它的信息。**如果上游标签贴错了，错误会一路传播到最终展示。**

| 优点 | 缺点 |
|------|------|
| 人类可读，调试方便 | 无时区语义，约定断裂就出 bug |
| 范围大（1000–9999 年） | 8 字节，比 TIMESTAMP 大一倍 |
| 改会话时区不影响已存的值 | 存错了就永远错了，修复需迁移数据 |


> 改会话时区不影响已存的值：DATETIME 是裸字符串，你改会话时区后重新读，拿到的还是原来那串字符。它稳定——不会因为环境配置变了就突然变值。

> 存错了就永远错了：正因为改时区不影响已存的值，所以如果当初存的是 UTC 字符串 "02:21:00"，你把会话时区改成 +08:00 再读，拿到的还是 "02:21:00"——改配置救不了它，只能用 SQL 把数据物理加 8 小时（迁移）

---

## 2. TIMESTAMP——自动换算的绝对时刻

**底层机制**：内部存 4 字节有符号整数（Unix 秒数），读和写时数据库根据**当前连接会话配置的时区**自动换算成墙钟字符串。

### 连接会话
这里的“会话”就是**一次数据库连接**。

你每次打开一个 MySQL 连接（比如程序里的连接池取了一条连接、或你在命令行敲了 `mysql -u root` 进入交互界面），就建立了一个“会话”。在这个会话里执行的每条 SQL，都共用这个连接的配置。

`time_zone` 就是一个会话级别的变量——你可以给不同的连接设置不同的时区：

```sql
-- 连接 A
SET time_zone = '+08:00';
SELECT CURRENT_TIMESTAMP;  -- "2026-09-21 10:21:00"

-- 连接 B（同一时刻，另一个连接）
SET time_zone = '+00:00';
SELECT CURRENT_TIMESTAMP;  -- "2026-09-21 02:21:00"
```

同一个 MySQL 服务器，两个连接看到不同的 `CURRENT_TIMESTAMP`——因为它们是两个不同的“会话”。

**"连接"和“会话"的关系**：在 MySQL 术语里，这两个词基本等同。严格来说“连接”是物理层面的 TCP 通道，“会话”是逻辑层面的一个执行上下文（包含各种会话变量、事务状态等）。一个连接对应一个会话，日常使用中不区分。

> 会话就是 SQL 执行的上下文

### 写入时发生了什么

你传入一个墙钟字符串（或用 `CURRENT_TIMESTAMP`），数据库先按当前会话的时区解析它，再转成 Unix 秒存入：

```
会话时区配置为 +08:00，传入 "2026-09-21 10:21:00"
→ 数据库理解为"上海时间 10:21"
→ 转成 Unix 秒 1789972860 存入
```

### 读取时发生了什么

完整链路：**数据库（换算）→ 驱动（贴标签）→ 应用程序 → 展示层**。

**第一步：数据库按会话时区换算成字符串**

这是 TIMESTAMP 与 DATETIME 最关键的区别——数据库在返回之前就做了换算：

```
底层存的：1789972860（绝对时刻）

会话时区配置为 +08:00：
→ 数据库换算后返回 "2026-09-21 10:21:00"

会话时区配置为 +00:00：
→ 数据库换算后返回 "2026-09-21 02:21:00"

同一行数据，不同时区的会话拿到不同字符串
```

**第二步：驱动把字符串变成程序中的时间对象**

驱动仍然需要贴时区标签，规则和 DATETIME 一样：

```
驱动配置 loc = +08:00
数据库返回 "2026-09-21 10:21:00"
驱动产出：2026-09-21 10:21:00 +08:00
```

**关键点**：此时驱动贴的标签必须和**数据库会话的时区配置**一致，否则贴错。例如数据库会话是 `+08:00` 返回了 `10:21`，但驱动 `loc` 配的是 `+00:00`，驱动就会把 `10:21` 理解为 UTC 的 10:21——又错了。

**第三步：应用程序拿到时间对象**

如果第一步和第二步的时区配置一致，此时的时间对象就是正确的。

**第四步：序列化给前端**

```json
"created_at": "2026-09-21T10:21:00+08:00"
```

**第五步：前端格式化展示**

```
用户在上海 → "10:21"
```

**TIMESTAMP 的优势**：即使写入时用错了时区，因为底层存的是绝对时刻，只要改对会话/驱动的时区配置，存量数据就能正确展示，无需迁移。

| 优点 | 缺点 |
|------|------|
| 底层是绝对时刻，数据本身不会存错 | **范围仅到 2038-01-19**（32 位溢出） |
| 改会话时区能正确换算展示 | 每次读写隐式依赖会话 `time_zone`，行为不透明 |
| 只占 4 字节 | 默认值 `CURRENT_TIMESTAMP` 有自动更新陷阱 |

## 3. BIGINT——纯数字 Unix 时间戳

**底层机制**：存一个 8 字节整数，代表从 `1970-01-01 00:00:00 UTC` 起的毫秒数（或秒数，取决于团队约定）。

### 写入时发生了什么

你直接传一个数字，数据库原样存入，不做任何解释：

```
INSERT ... VALUES (1789972860000);
列里存的：1789972860000
```

### 读取时发生了什么

完整链路：**数据库 → 驱动 → 应用程序 → 展示层**。每一层都没有歧义。

**第一步：数据库返回原始数字**

```
SELECT created_at;
→ 驱动收到字节流：1789972860000
```

数据库原样返回，没有任何换算。

**第二步：驱动把数字变成程序中的时间对象**

Unix 毫秒**本身就定义了时区锚点**（`1970-01-01 00:00:00 UTC`），不需要任何外部配置来“贴标签”：

```
驱动产出：time.UnixMilli(1789972860000)
→ 时刻 = 2026-09-21T02:21:00Z（UTC）
```

没有“认定”或“假设”，数学上就是这个值。

**第三步：应用程序拿到时间对象**

这个 `time.Time` 的时刻是精确的，不存在标签贴错的可能。

**第四步：序列化给前端**

可以输出两种格式：

```json
// 方式一：Unix 毫秒
"created_at": 1789972860000

// 方式二：RFC 3339 UTC 字符串
"created_at": "2026-09-21T02:21:00Z"
```

**第五步：前端格式化展示**

```
Unix 毫秒 → new Date(1789972860000) → 按浏览器时区展示
RFC 3339 → new Date("2026-09-21T02:21:00Z") → 按浏览器时区展示

用户在上海 → "10:21"
用户在纽约 → "2026-09-20 22:21"
```

**BIGINT 的优势**：全链路没有任何“约定”或“配置”依赖，时区只在最终展示时才介入。

| 优点 | 缺点 |
|------|------|
| 无时区歧义，彻底消除“贴标签”问题 | 人类不可读，调试需要转换 |
| 排序比较是纯数字操作，性能最优 | 应用层需自行转 `Date` 对象 |
| 范围极大（毫秒存 BIGINT 可到约 2.25 亿年后） | 需约定秒还是毫秒（团队规范） |

---

## 三者对比总表

| | `DATETIME` | `TIMESTAMP` | `BIGINT` |
|---|---|---|---|
| **存储内容** | 格式化字符串 | 4 字节 Unix 秒 | 8 字节 Unix 毫秒 |
| **存储大小** | 8 字节 | 4 字节 | 8 字节 |
| **表示范围** | 1000–9999 年 | 1970–2038 年 ⚠️ | 约 2.25 亿年 |
| **写入值取决于什么** | 你传入的字符串本身 | 会话 `time_zone` 换算 | 你传入的数字本身 |
| **读取时数据库是否换算** | 否（原样返回） | 是（按会话 `time_zone`） | 否（原样返回） |
| **读取时驱动是否需要贴标签** | 是（`loc` 配置） | 是（`loc` 配置） | 否（数学定义，无歧义） |
| **标签贴错的后果** | 全链路传播错误 | 全链路传播错误 | 不存在此问题 |
| **SQL 调试可读性** | 最好 | 好 | 差 |
| **排序性能** | 字符串比较 | 整数比较 | 整数比较（最优） |

---

## 怎么选

| 场景 | 推荐 | 理由 |
|------|------|------|
| 新项目、新表 | **BIGINT** | 消除时区歧义，避免 2038 问题 |
| 遗留系统，只想减 bug | **DATETIME 统一存 UTC** | 不改列类型，靠团队约定收窄风险 |
| 短生命周期、需要自动换算展示 | TIMESTAMP | 方便，但 2038 年前要迁走 |

**最佳实践**：后端 API 输出 Unix 时间戳或 RFC 3339 UTC 字符串，前端用 `Intl.DateTimeFormat` 按用户浏览器时区格式化。全链路只有一种“源”，展示端本地化。
