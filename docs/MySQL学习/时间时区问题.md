# 数据库时间类型科普：DATETIME、TIMESTAMP、BIGINT

## 问题的起点

在数据库里存“一个时间”听起来很简单，但不同类型的底层机制完全不同，选错了会埋下时区 bug。下面用具体例子把三种类型讲清楚。

---

## 1. DATETIME——裸字符串

**底层机制**：存一个格式化字符串，不带任何时区信息。

```
写入：INSERT ... VALUES (CURRENT_TIMESTAMP);
MySQL 服务器时区 = UTC
列里存的："2026-09-21 02:21:00"（8 字节）
```

**读取**：原样返回字符串，不换算、不解释。

```
SELECT created_at;
→ "2026-09-21 02:21:00"
```

**谁有责任解释这串数字是什么时区？** 没人。这是 DATETIME 最大的特点，也是最大的坑——**写和读必须靠约定对齐**。

| 优点 | 缺点 |
|------|------|
| 人类可读，调试方便 | 无时区语义，约定断裂就出 bug |
| 范围大（1000–9999 年） | 8 字节，比 TIMESTAMP 大一倍 |
| 改会话时区不影响已存的值 | 存错了就永远错了，修复需迁移数据 |

---

## 2. TIMESTAMP——自动换算的绝对时刻

**底层机制**：内部存 4 字节有符号整数（Unix 秒数），读和写时 MySQL 根据当前会话的 `time_zone` 自动换算成墙钟字符串。

```
写入（会话 time_zone='+08:00'，上海 10:21）：
MySQL → 1789972860（内部存储）

换一个会话读（time_zone='+00:00'）：
SELECT created_at;
→ "2026-09-21 02:21:00"（自动换成 UTC 展示）

换回 time_zone='+08:00' 再读：
→ "2026-09-21 10:21:00"（自动换回上海展示）
```

同一个底层值，不同时区的会话看到不同墙钟——**这就是“翻译官”的行为**。

| 优点 | 缺点 |
|------|------|
| 底层是绝对时刻，数据本身不会存错 | **范围仅到 2038-01-19**（32 位溢出） |
| 改会话时区能正确换算展示 | 每次读写隐式依赖 `time_zone`，行为不透明 |
| 只占 4 字节 | 默认值 `CURRENT_TIMESTAMP` 有自动更新陷阱 |

---

## 3. BIGINT——纯数字 Unix 时间戳

**底层机制**：存一个 8 字节整数，代表从 `1970-01-01 00:00:00 UTC` 起的毫秒数（或秒数，取决于约定）。

```
写入：INSERT ... VALUES (1789972860000);
列里存的：1789972860000

读取：SELECT created_at;
→ 1789972860000
```

没有字符串，没有时区标签，没有换算。一个数字就是全世界唯一的一个瞬间。

| 优点 | 缺点 |
|------|------|
| 无时区歧义，彻底消除“贴标签”问题 | 人类不可读，调试需要转换 |
| 排序比较是纯数字操作，性能最优 | 应用层需自行转 `Date` 对象 |
| 范围极大（毫秒存 BIGINT 可到约 2.25 亿年后） | 需约定秒还是毫秒（团队规范） |

---

## 三者对比总表

| | `DATETIME` | `TIMESTAMP` | `BIGINT` |
|---|---|---|---|
| **存储内容** | 格式化字符串 | 4 字节 Unix 秒 | 8 字节 Unix 毫秒 |
| **存储大小** | 8 字节 | 4 字节 | 8 字节 |
| **表示范围** | 1000–9999 年 | 1970–2038 年 ⚠️ | 约 2.25 亿年 |
| **时区语义** | 无（裸字符串） | 有（自动换算） | 无（天然无歧义） |
| **写错了能修吗** | 需迁移数据 ✗ | 换时区即可展示正确 ✓ | 不存在“存错时区”问题 |
| **SQL 调试可读性** | 最好 | 好 | 差 |
| **排序性能** | 字符串比较 | 整数比较 | 整数比较（最优） |

---

## 怎么选

| 场景 | 推荐 | 理由 |
|------|------|------|
| 新项目、新表 | **BIGINT** | 消除时区歧义，避免 2038 问题 |
| 遗留系统，只想减 bug | **DATETIME 统一存 UTC** | 不改列类型，靠团队约定收窄风险 |
| 短生命周期、需要自动换算展示 | TIMESTAMP | 方便，但 2038 年前要迁走 |

**最佳实践**：后端 API 输出 Unix 时间戳或 RFC 3339 UTC 字符串，前端用 `Intl.DateTimeFormat` 按用户浏览器时区格式化。全链路只有一种“源”，展示端本地化。
