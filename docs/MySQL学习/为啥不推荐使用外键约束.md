## 为什么现在mysql都不推荐用外键约束
“不推荐用外键”这个说法，更准确地理解是：在**互联网的高并发、分布式架构**下，物理外键（数据库层面强制的约束）带来的麻烦往往超过它的收益。这并非 MySQL 本身的缺陷，而是架构演进和场景权衡的结果。

### 🚧 性能与并发：隐形的“锁”与“查”

外键约束在数据库层面是**强制性**的，这意味每一次写入或删除，数据库都必须额外执行检查，从而引入开销和锁竞争。

*   **额外的查询开销**：当你向子表插入数据时，数据库必须先去父表确认对应的记录存在。在高频写入场景下，这个“额外一次查询”会被急剧放大，成为性能瓶颈。有测试显示，在有外键的情况下，批量插入可能比无外键慢**32.7%**。
*   **锁竞争与死锁**：为了保证一致性，外键检查通常会在父表记录上加**共享锁（S锁）**。如果此时另一个事务正好要更新父表的那条记录（需要排他锁 X 锁），两者就会冲突，导致等待甚至死锁。在“双十一”这类高并发场景下，这种锁争用可能直接把服务拖垮。

### 🔧 架构演进：外键是“单机思维”的产物

现代互联网应用普遍采用**分库分表**和**微服务**架构，而物理外键的设计前提是“所有关联数据都在同一个数据库实例里”。

*   **分库分表后失效**：一旦你把数据拆分到不同的数据库或服务器上，MySQL 的外键约束**在物理上就无法跨库生效了**。你必须自己想办法维护跨库的数据一致性。
*   **阻碍在线 DDL 与迁移**：有外键约束的表，在进行结构变更（如修改列类型、增加字段）或数据迁移时会变得非常麻烦。像 `gh-ost`、`pt-online-schema-change` 这类在线 DDL 工具，以及 Shopify 的 `Ghostferry` 等数据迁移工具，都明确表示**不支持或难以处理有外键的表**。这意味着一次简单的表结构变更可能变成停机维护事故。

### 💡 那数据一致性怎么保证？

放弃物理外键，不代表放弃数据关联，而是把控制权从数据库收回到**应用层**，这被称为“**逻辑外键**”。

*   **应用层校验**：在业务代码里，插入订单前先检查用户是否存在；删除用户时，由程序逻辑负责清理或转移其关联的订单。
*   **事务与补偿**：利用数据库的本地事务来保证单库操作的原子性；对于跨库场景，则通过分布式事务或最终一致性方案（如定时对账修复）来兜底。

### ⚖️ 所以，外键还能用吗？

当然可以，但它更适合**单机、数据量小、并发不高**的场景，比如内部管理系统、早期创业项目。在这些场景下，外键能帮你用极低的开发成本保证数据不错乱。

但对于任何预期会有高并发写入、或者未来需要做分库分表的系统，从一开始就避开物理外键，是更稳妥的选择。


## 为啥外键约束在分库分表后就失效了
这个问题的核心在于：**外键约束是数据库实例内部的一种机制，它无法跨越多个独立的数据库实例去执行检查。**

要理解这一点，需要先看清外键约束到底是在哪里、以什么方式生效的。

### 外键约束的“势力范围”仅限于单个数据库实例

当你创建一个外键时，比如：

```sql
ALTER TABLE orders
ADD CONSTRAINT fk_user
FOREIGN KEY (user_id) REFERENCES users(id);
```

这个约束是**登记在 MySQL 服务进程内部**的。它生效的前提是：`orders` 表和 `users` 表都在**同一个 MySQL 实例**里，由同一个进程管理。

当有数据写入 `orders` 时，这个 MySQL 进程可以直接去查自己管理的 `users` 表，确认 `user_id` 是否存在。整个过程不需要跨网络，也不需要跟其他进程协调，因为它对自己管辖范围内的所有表都有完全的控制权。

### 分库分表后，父表和子表可能已经“分家”了

分库分表的核心操作，就是把原本放在一个实例里的数据，拆分到多个实例上。常见的拆分方式有两种，都会直接破坏外键生效的前提：

**情况一：父表和子表被拆到了不同的数据库实例**

比如，`users` 表留在实例 A，`orders` 表被拆分到了实例 B。这时，实例 B 上的 `orders` 表如果还保留着指向 `users` 表的外键，会发生什么？

实例 B 的 MySQL 进程在插入 `orders` 时，需要去检查 `users` 表里有没有对应的 `user_id`。但 `users` 表根本不在实例 B 上，实例 B 的进程**没有权限、也没有能力**去访问实例 A 的数据。它无法执行这个检查。

MySQL 在语法层面甚至不允许你创建一个指向另一个实例上表的外键——因为外键定义里只能写表名，不能写“哪个实例上的哪个表”。所以，在分库分表后，这些外键约束要么被直接删除，要么在迁移过程中就无法保留。

**情况二：父表本身也被分片了**

即使 `users` 和 `orders` 都在同一个逻辑库中，但如果 `users` 表本身也做了分片，比如按 `user_id` 取模，一部分用户在实例 A，另一部分在实例 B。那么一条 `orders` 记录要检查的 `user_id`，可能恰好落在另一个实例上。

这时，插入 `orders` 的实例无法确定该去哪个实例检查，也无法保证检查时那个实例是可用的。外键约束同样失效。

### 本质上，外键依赖的是“本地事务 + 本地锁”

外键约束能生效，背后依赖的是数据库的**本地事务**和**本地锁机制**。当插入子表记录时，数据库会在同一个事务里，对父表记录加共享锁，然后检查存在性。这一切都在**同一个进程、同一个事务上下文**中完成。

分库分表之后，父表和子表分属不同的进程和事务上下文。要跨实例检查，就需要引入**分布式事务**或**两阶段提交**，而这正是外键约束机制本身**不提供**的。外键约束的设计里，根本没有“跨实例协调”这个概念。

所以，不是外键“失效”了，而是分库分表这个动作，从根本上**移除了外键约束赖以生效的基础设施**——单一实例的本地控制权。数据库无法再替你做这个检查，你只能把这份责任转移到应用层，用逻辑外键去维护数据关联。

## 外键约束的删除更新行为
外键约束的删除和更新行为，由两个独立的选项控制：`ON DELETE` 和 `ON UPDATE`。它们定义了当父表（被引用的表）中的记录被删除或更新时，子表（持有外键的表）中对应的记录该如何处理。

### 四种核心行为

MySQL（InnoDB引擎）主要支持以下四种行为：

**1. RESTRICT（拒绝）**
*   **行为**：拒绝父表的删除或更新操作。如果子表中存在匹配的记录，父表操作会直接报错失败。
*   **典型场景**：这是**默认行为**。用于严格保护数据，防止意外删除仍有子记录关联的父数据。例如，还有订单的用户不能被删除。

**2. CASCADE（级联）**
*   **行为**：父表操作会“连锁”到子表。父表记录被删除，子表匹配记录也**自动删除**；父表记录的主键被更新，子表匹配的外键值也**自动更新**。
*   **典型场景**：用于强依赖关系，子数据脱离父数据就没有意义。例如，删除一个订单，其包含的所有订单明细也应一并删除。

**3. SET NULL（置空）**
*   **行为**：父表记录被删除或更新时，子表匹配记录的外键列被**设置为 NULL**。
*   **前提条件**：外键列必须允许为 NULL（即没有 `NOT NULL` 约束），否则该操作会失败。
*   **典型场景**：用于弱关联。例如，一个产品被删除，但历史订单记录还需保留，此时可以将订单中的产品 ID 置空。

**4. NO ACTION（无操作）**
*   **行为**：在 MySQL 中，它的效果与 `RESTRICT` **完全相同**，都是拒绝父表操作。
*   **说明**：虽然 SQL 标准中 `NO ACTION` 允许延迟检查，但 MySQL 不支持延迟约束检查，因此它被当作 `RESTRICT` 处理。

### 使用时的关键点

除了行为本身，还有几个细节需要注意：

*   **默认行为是 RESTRICT**：如果在定义外键时没有指定 `ON DELETE` 或 `ON UPDATE`，默认就是 `RESTRICT`，会阻止任何会破坏引用完整性的操作。
*   **SET DEFAULT 不被支持**：虽然语法上可能允许，但 InnoDB 会拒绝 `SET DEFAULT` 行为，视为无效。
*   **自引用表的限制**：如果表的外键指向自身，`ON UPDATE CASCADE` 或 `ON UPDATE SET NULL` 会导致 MySQL 将其行为类似 `RESTRICT`，以防止无限循环。但 `ON DELETE` 的级联或置空行为是允许的。
*   **级联深度有限制**：级联操作的嵌套深度不能超过 **15 层**。

所以，`ON DELETE` 和 `ON UPDATE` 让你能精确控制数据一致性的“松紧度”：从严格保护（RESTRICT）到完全托管（CASCADE），或是保留关联但断开连接（SET NULL）。


## 级联深度怎么理解
“级联深度不能超过 15 层”这个限制，理解起来容易产生一个误区：它**不是指一张表里嵌套了多少个外键**，而是指**级联操作沿着外键关系“跳转”的次数**。

### 先看一个简单的级联链

假设有三张表，形成一条链：

```
A (父表)
  ↑ 外键
B (子表)
  ↑ 外键
C (子表)
```

这里 B 有一个外键指向 A，C 有一个外键指向 B。外键都设置了 `ON DELETE CASCADE`。

现在删除 A 中的一条记录：
1.  **第 1 层**：A 的记录被删除，触发 B 中匹配记录的删除。
2.  **第 2 层**：B 的记录被删除，又触发 C 中匹配记录的删除。

这里级联深度就是 **2**。如果 C 后面还有 D 指向 C，D 后面还有 E……每多一层引用关系，深度就加 1。MySQL 限制这个链条最长只能有 **15 层**。

### 为什么会有这个限制？

核心原因是**防止无限递归和失控的连锁反应**。

考虑一种极端情况：如果表 A 的外键指向自己（自引用），并且设置了 `ON DELETE CASCADE`。删除 A 中一条记录，可能触发删除它的子记录，子记录又触发删除孙记录……如果没有深度限制，这个操作可能永远停不下来，或者瞬间删除海量数据，把数据库拖垮。

即使不是自引用，一个设计复杂的 schema 也可能形成很长的级联链。15 层的限制，是 MySQL 在“功能可用”和“系统安全”之间划的一条线。超过这个深度，数据库会直接报错，拒绝执行，而不是冒险继续。

### 一个容易混淆的点

“级联深度”和“外键数量”是两回事。

*   一张表可以有**很多个外键**，分别指向不同的父表。这不叫“深度”，这叫“宽度”。删除这张表的记录，会同时触发对多个父表的检查（但通常是 RESTRICT 行为，不会级联）。
*   深度只关心**沿着一条引用路径能走多远**。比如 A ← B ← C ← D，这是一条深度为 3 的路径。

所以，当你看到“级联深度不能超过 15 层”时，可以把它理解为：**从最初被操作的那张表出发，沿着外键关系一路“传染”下去，最多只能传染 15 次。** 超过这个次数，MySQL 就会踩刹车，防止局面失控。
