## Codex App Server 压测进程分析

### 结论

本轮压测任务 ID 是 `c38dbb3c-b0bc-4191-b20a-d5cae4d23938`。配置为并发 10、开启 `project_tools` stdio MCP、关闭多 MCP server 验证、开启 Codex App Server。

结果确认：

- 10 个请求全部成功；总耗时 34.8 秒，平均 28.2 秒，最快 20.7 秒，最慢 34.7 秒。
- 真实服务进程树 RSS 峰值为 1.2 GB，CPU 峰值为 280.7%。
- 压测期间共出现 65 个进程，但各进程峰值 RSS/CPU 相加分别是 1470.5 MB / 291.1%，不能当作同一秒的真实峰值。
- 本轮确实使用 Codex App Server 协议：10 个请求只共享一组长驻 `codex app-server` 父子进程，而不是每个请求 spawn 一个 `codex exec`。
- 压测期间出现过 10 个 `project_tools` stdio MCP 子进程。它们是自定义工具 server 的注册进程；本轮 prompt 是纯作文任务，现有汇总没有记录真实的 MCP 工具调用事件，不能仅凭这些进程证明模型实际调用了工具。

### 常驻进程说明

压测结束后服务进程树仍有 4 个进程是当前实现的预期状态：

| 进程 | PID / PPID | 是什么 | 为什么常驻 |
| --- | --- | --- | --- |
| Next.js 服务 | 16952 / 16946 | `next-server (v16.3.7)` | 开发服务器正在运行，承载监控页和 API。 |
| Turbopack PostCSS | 16956 / 16952 | Next.js dev 样式编译 worker | 开发模式下处理 Tailwind/PostCSS 样式。 |
| Codex App Server Node 包装 | 17664 / 16952 | `codex.js app-server` | 解析平台并启动真正的 Codex 二进制。 |
| Codex App Server Rust 主进程 | 17670 / 17664 | `codex app-server` | 长驻 JSON-RPC server，等待后续请求复用。 |

其中前两个是 `pnpm dev` 需要的常驻服务。后两个是 App Server 模式有意保留的单例连接：请求结束时只 `thread/unsubscribe` 并卸载 ephemeral thread 和 MCP 子进程，不会主动杀掉整个 app-server。这样下一次请求可以复用连接和二进制，避免冷启动开销。当前没有空闲 TTL、监控页停止按钮或压测结束自动 dispose 逻辑，所以它们会一直保留到 Next.js 重启、进程退出或手动清理。

### 协议证据

进程树是：

```text
next-server 16952
  └─ codex.js app-server 17664
      └─ codex app-server 17670
          ├─ project_tools MCP 17874...17955
          └─ SkyComputerUseClient notify ...
```

`17664` 是 Node 包装进程，负责解析平台并启动 `@openai/codex`；`17670` 是真正的 Rust 主进程，处理 JSON-RPC over stdio。10 个请求通过 `thread/start` 创建 ephemeral thread，通过 `turn/start` 提交回合，结束后再用 `thread/unsubscribe` 触发线程和 MCP runtime 卸载。

### 启动原因

- **Next.js 服务 / Turbopack PostCSS**：承载 `/monitor` 页面和 API；PostCSS worker 是开发模式样式编译需要的常驻进程。
- **Codex app-server Node 包装**：启动真正的 Codex 平台二进制。
- **Codex app-server Rust 主进程**：长驻 JSON-RPC server，是本轮所有请求、thread、模型回调和 MCP runtime 的宿主。
- **Git 检查链**：app-server 启动时检查 OpenAI plugins 和 Langfuse marketplace 远端 HEAD，避免本地插件缓存过期。每组包含 `git ls-remote`、`git remote-https`、`git-remote-https`。
- **`project_tools` stdio MCP**：每个请求/thread 的 MCP runtime 初始化时启动一个独立 Node 子进程。10 个请求对应 10 个进程，请求结束后卸载。
- **Zsh 环境快照链**：Codex/thread 初始化 shell 环境，读取 `.zshrc` 并捕获 alias、function、export 等状态。链中还有少量 Node、`tail`、`printf`、`dirname` 等短命子进程。
- **`SkyComputerUseClient` 通知**：全局 turn-ended notify hook 拉起的短命通知进程。只观察到 9 个是 1 秒采样可能错过第 10 个短命进程。
- **未识别短命 Node**：只采样到一次，命令名只显示 `(node)`，无法从现有 1 秒快照确定具体来源。

### 注意

监控 UI 中的“Codex”类型是整个 Codex 进程树分类。因此 `SkyComputerUseClient` 通知进程和 `project_tools` MCP 子进程都会显示成 Codex；不能只看类型列判断是否是 MCP 工具进程。截图右侧的 `21051`、`21053`、`21080`、`21081`、`21083` 都是 `SkyComputerUseClient turn-ended` 通知进程，真正的 MCP 子进程是 `17874`、`17875`、`17876`、`17877`、`17878`、`17879`、`17882`、`17883`、`17884`、`17955`。
