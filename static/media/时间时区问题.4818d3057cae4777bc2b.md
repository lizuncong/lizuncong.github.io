# 计算机系统里的时间：从写入到展示

## 前提：时间在计算机里的三种形态

| 形态 | 例子 | 特点 |
|------|------|------|
| **Unix 时间戳** | `1789972860` | 一个数字，全世界唯一，无歧义 |
| **UTC 墙钟** | `2026-09-21T02:21:00Z` | 人类可读的时刻，标准零时区 |
| **本地墙钟** | `2026-09-21 10:21:00`（上海） | 挂了时区标签的墙钟 |

关键认知：**墙钟本身没有时区标签**。`02:21:00` 这串数字本身不携带任何时区信息，它只是一组数字。时区是“贴”上去的元数据。

---

## 完整链路：四层

```
[写入方] → [存储层] → [读取方] → [展示层]
```

### 第一层：写入方产生一个时刻

写入方有两种方式产生“现在是什么时间”：

**方式一：让数据库自己算**

```sql
INSERT INTO messages (created_at) VALUES (CURRENT_TIMESTAMP);
```

数据库服务器收到后，用自己的时钟和自己的时区设置，算出当前时间：

```
数据库时区 = UTC
CURRENT_TIMESTAMP → "2026-09-21 02:21:00"（UTC 墙钟）
→ 写入列，存的就是这串裸数字
```

**方式二：让应用层算好再传**

```go
timestamp := time.Now().UnixMilli()  // 1789972860000
// 通过参数传给 SQL
db.Exec("INSERT INTO messages (created_at) VALUES (?)", timestamp)
```

Unix 时间戳没有时区概念，不管你在哪台机器上算，`1789972860000` 代表的都是同一个瞬间。

但列类型是 `DATETIME`，驱动在写入前要做一次**转换**：把这个时刻转成某个时区的墙钟字符串再存。转成哪个时区？由驱动的配置决定。

---

### 第二层：存储层（数据库）

数据库的 `DATETIME` 列本质上就是一个**格式化的字符串容器**：

```
列里存的：2026-09-21 02:21:00
```

数据库**不存储时区信息**。这串数字是 UTC 还是上海时间，数据库不知道，也不关心。

这就是问题的种子：**存的时候没贴标签，读的时候就得靠猜。**

---

### 第三层：读取方（应用程序）

应用程序从数据库读出 `DATETIME`，拿到裸字符串：

``"2026-09-21 02:21:00"``

现在要把它还原成一个精确的“时刻”。但缺少关键信息：**这串数字是什么时区的？**

驱动的 `loc` 参数就是在回答这个问题。它相当于一个约定：

> “我认定数据库里存的都是 Asia/Shanghai 时区的墙钟。”

于是驱动把这串数字原样装进 `time.Time`，贴上上海标签：

```
2026-09-21 02:21:00 +08:00
```

如果数据库确实存的是上海墙钟，这个还原是正确的。

如果数据库实际存的是 UTC 墙钟，这个还原就是错的——数字没变，但标签贴错了。

---

### 第四层：展示层（前端）

前端收到 JSON：

```json
"created_at": "2026-09-21T02:21:00+08:00"
```

`Intl.DateTimeFormat` 会把这个带时区的时刻转换成用户浏览器所在时区的显示：

```
用户在上海浏览器 → "02:21"（因为它确实就是上海时间 02:21）
```

前端没做错任何事，它忠实地展示了后端给它的信息。**错误在上游就已经产生了。**

---

## Bug 是怎么发生的

写和读之间有一个**隐含契约**：

> “写的时候用什么时区的墙钟，读的时候就用什么时区去解读。”

这个契约靠什么保证？靠写入方和读取方**配置一致**。

两种写入方式用不同的时钟源：

| 写入方式 | 时钟来源 | 受谁控制 |
|---------|---------|---------|
| `CURRENT_TIMESTAMP` | 数据库服务器 | 数据库的 `time_zone` 设置 |
| 应用传时间戳 + 驱动转换 | 驱动的 `loc` 配置 | 应用代码的 DSN |

当这两者**不一致**时，同一个表里就混着两种“方言”的墙钟，读取方只认一种方言，另一种就会被误读。

---

## 怎么修

有三种思路，从轻到重：

**1. 统一数据库时区（最小改动）**

在连接字符串里加 `time_zone='+08:00'`，让 `CURRENT_TIMESTAMP` 返回的也是上海墙钟。契约重新对齐，但依赖配置永远不出错。

**2. 统一用 UTC 存储（推荐）**

所有写入方都传 UTC 时间戳或 UTC 墙钟，驱动的 `loc` 设为 `time.UTC`。展示层拿到 UTC 时刻后按用户本地时区格式化。这是业界标准做法。

**3. 全链路 Unix 时间戳（最彻底）**

存储列改为 `BIGINT`，存 Unix 毫秒。无时区概念，不存在“贴标签”的问题。但需要改表结构和所有 SQL。
