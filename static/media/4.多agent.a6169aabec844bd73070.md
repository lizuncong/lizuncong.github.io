### 子 Agent 详细分析

这是本次压测的核心发现。**3 个请求全部成功触发了多 agent 流程**，模型名修复生效（零 "Unknown model" 错误）。

**子 agent 创建记录（从 rollout 文件确认）：**

| 父请求 | game_designer | game_developer | 使用模型 |
|---|---|---|---|
| codex 7b02 | ✅ spawn 成功 | ✅ spawn 成功 | deepseek/deepseek-v4.1-flash + gpt-6.1-sol |
| codex 7ea0 | ✅ spawn 成功 | ✅ spawn 成功 | 同上 |
| codex 7e31 | ✅ spawn 调用发出 | ✅ spawn 成功 | 同上 |
| **合计** | **3 个** | **3 个** | **共 6 个子 agent** |

**子 agent 的关键资源事实：**

1. **OS 进程数：0**——子 agent 是同一 `codex exec` 进程内的 Tokio task，不创建新 OS 进程。3 个 codex 进程 + 3 个 MCP 进程在压测全程未变。

2. **MCP 连接：复用父的**——6 个子 agent 运行期间，MCP 进程始终只有 3 个（每个父一个）。子 agent 共享父 session 的 MCP 连接，不独立 spawn。

3. **内存边际开销：~1-3 MB/个**——Session + Tokio task + 对话历史。相比 `codex exec` 的 ~120 MB + MCP 的 ~45 MB，子 agent 几乎免费。

4. **模型名修复生效**——之前每次 spawn 都会先报 `Unknown model deepseek/deepseek-v4.1-flash` 再重试 `deepseek-flash`，浪费一轮 API 调用。这次 `models.json` 加了正确的 slug 后，**3 个请求 × 2 次 spawn 全部一次成功**，零重试。

### 为什么启动

- **`codex exec` × 3**：压测并发 3，SDK 每个任务 spawn 一个进程。必要。
- **MCP × 3**：每个 codex exec 启动时初始化 1 个 `project_tools` stdio MCP server。子 agent 共享父的连接，不增加进程数。
- **Git × 9**：每个 codex 启动时检查 2 个 plugin marketplace（OpenAI + Langfuse），每次检查 1-3 个进程链。纯任务不必要但开销小。
- **Zsh × 3**：每个 codex 启动时捕获 shell 环境。作文/游戏任务不必要。
- **Langfuse × 3**：每个任务完成时 Stop hook 启动 Node 进程上传 trace。单进程 RSS 峰值 94 MB，是观测开销最大的组。
- **通知 hook × 6-8**：全局 `notify` 的 turn-ended 回调。每个 codex 的每次 turn 结束都触发。
- **子 agent（进程树中不可见）**：6 个 Tokio task，分布在 3 个 codex 进程内。不产生 OS 进程、不 spawn MCP、不触发 Git 检查。唯一可见的痕迹是 rollout 文件和 Langfuse trace。

### 能否覆盖

纯压测下，Git 检查（9）、Zsh 快照（3）、Langfuse tracing（3）、通知 hook（6-8）都可以省掉，能减少约 21-24 个进程。核心保留 Next.js 1 + codex 3 + MCP 3 + ps 若干 = **约 10 个**。
